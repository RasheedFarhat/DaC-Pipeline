This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo does

Detection-as-Code (DaC) CI/CD pipeline that manages Wazuh SIEM threat detection rules as version-controlled code. Sigma YAML rules are the single source of truth; a custom compiler translates them to Wazuh XML via an AST walker and Jinja2 template, then deploys them to a live Wazuh manager via its REST API.

## Commands

```bash
# Set up environment (required before anything else)
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
pre-commit install

# Run tests
make test
# or: venv/bin/python3 -m pytest tests/ -v --tb=short
# Single test: venv/bin/python3 -m pytest tests/test_check_rule_ids.py -v

# Full build pipeline (clean → compile → validate IDs → test)
make all

# Individual steps
make compile    # compile_sigma.py: Sigma YAML → build/wazuh/*.xml
make validate   # check_rule_ids.py: validate IDs and UUID linkage (requires compile first)
python scripts/validate_sigma.py  # sigma-cli syntax check on rules/sigma/

# Dry-run deployment (simulates deploy without touching Wazuh)
python scripts/deploy_rule.py --dry-run

# Simulate GitHub Actions locally (requires act + docker)
make ci
```

## Architecture

### Build pipeline (must run in order)

1. **`scripts/validate_sigma.py`** — runs `sigma check` on `rules/sigma/` to verify YAML syntax
2. **`scripts/compile_sigma.py`** — the core compiler:
   - Walks Sigma rules in `rules/sigma/`, parses each via pySigma's `SigmaCollection`
   - Recursively evaluates the detection AST (`ConditionOR`, `ConditionAND`, `ConditionNOT`, leaf nodes)
   - Maps Sigma field names to Wazuh field names via `FIELD_MAPPINGS` dict inside `evaluate_ast()`
   - Renders each compiled rule via `templates/wazuh_rule.xml.j2` (Jinja2)
   - Writes output to `build/wazuh/` (gitignored — ephemeral build artifact)
   - Auto-assigns stable Wazuh rule IDs from `id_registry.json`; commits new entries back
3. **`scripts/check_rule_ids.py`** — validates `build/wazuh/` against `rules/sigma/`:
   - Wazuh IDs must be integers ≥ 200000
   - Every XML file must have a `<!-- sigma_uuid:UUID -->` comment linking it to a Sigma rule
   - No duplicate IDs or UUIDs allowed

### Key files

| File | Purpose |
|---|---|
| `rules/sigma/*.yml` | Source of truth — Sigma detection rules |
| `build/wazuh/*.xml` | Compiled output — gitignored, regenerated by compile step |
| `id_registry.json` | Persistent map of `sigma_uuid → wazuh_id`; **must be committed** when new rules are added |
| `templates/wazuh_rule.xml.j2` | Jinja2 template for Wazuh XML output |
| `pipeline.yaml` | Central config for directory paths and deploy settings |
| `configs/agent.conf` | Wazuh agent group config (deployed alongside rules) |

### Deployment (`scripts/deploy_rule.py`)

- Reads settings from `pipeline.yaml` and env vars (see `.env` or `Settings` class)
- Bundles all XML files in `build/wazuh/` into one file (`sigma_custom_rules.xml`) — this is intentional to avoid a Wazuh restart race condition
- Reconciles remote state: deletes orphaned rules from Wazuh, with a hard abort if >5 rules would be deleted (blast radius safeguard)
- Retries transient API failures (429, 5xx, connection errors) with exponential backoff via `tenacity`
- Required env vars: `WAZUH_USER`, `WAZUH_PASSWORD`; optional: `WAZUH_API_URL`, `WAZUH_INSECURE`, `WAZUH_CA_BUNDLE`

### CI/CD workflows

- **`integrate_rulesets.yml`** — CI on push/PR to `main`/`dev`: tests → validate sigma → compile → validate IDs → upload artifact
- **`deploy.yml`** — CD via manual `workflow_dispatch` on a self-hosted runner: same steps + deploy to Wazuh
- **`pr_dry_run.yml`** — runs `deploy_rule.py --dry-run` on PRs and posts the output as a comment

## Important constraints

**No official pySigma Wazuh backend exists on PyPI.** Sigma rules are validated using `pysigma-backend-elasticsearch` (proves compilability), but the actual Wazuh XML is generated by the custom AST walker in `compile_sigma.py`, not by a pySigma backend plugin.

**`id_registry.json` must be committed after adding new rules.** `compile_sigma.py` auto-assigns Wazuh IDs and writes them here. If you add a rule and don't commit the registry update, the next build will assign different IDs, breaking stable rule references in the SIEM.

**Wazuh rule IDs must be ≥ 200000.** IDs 0–99999 are Wazuh built-ins; 100000–199999 were previously used but are now reserved. `check_rule_ids.py` enforces this.

**Adding a new Sigma field mapping** requires editing `FIELD_MAPPINGS` inside `evaluate_ast()` in `scripts/compile_sigma.py` (line ~97).

**The `--dry-run` remote diff** in `deploy_rule.py` has not been validated against a live Wazuh manager. If the API response shape differs, it silently treats all rules as new.
